# Repository Guidelines

This is **hgsigns.nvim** — a Mercurial-backend fork of
[gitsigns.nvim](https://github.com/lewis6991/gitsigns.nvim) by lewis6991.
The repository lives as a git worktree at `mercurial/` alongside the upstream
mirror at `main/`.  The upstream remote is tracked as `upstream`.

## Project Structure & Module Organization

- Core Lua modules live in `lua/hgsigns/` (config, handlers, utilities).
- Entry point: `lua/hgsigns.lua` and `plugin/hgsigns.lua`.
- Help files under `doc/` get regenerated by `gen_help.lua`.
- Specs plus fixtures sit in `test/`, relying on helpers in `test/gs_helpers.lua`.
- Tooling binaries (Stylua, nvim-test, EmmyLua) are cached in `deps/`.
- Porting decisions and VCS translation tables live in `PORTING.md`.

### Rename Map (upstream → this fork)

Every runtime identifier follows a single lowercase name:

| gitsigns (upstream)              | hgsigns (this fork)              |
|----------------------------------|----------------------------------|
| `lua/gitsigns/`                  | `lua/hgsigns/`                   |
| `require('hgsigns')`            | `require('hgsigns')`             |
| `:Hgsigns <action>`             | `:Hgsigns <action>`              |
| Highlight group `Hgsigns*`      | `Hgsigns*`                       |
| Buffer variable `b:hgsigns_*`   | `b:hgsigns_*`                    |
| Autocommand `User GitsignsUpdate`| `User HgsignsUpdate`             |

## Build, Test, and Development Commands

- `make build`: run Stylua over `lua/` + `test/`, then regenerate help files before committing.
- `make test [FILTER=pattern]`: execute the functional suite via nvim-test with the default Neovim runner.
- `make test-all`: run the suite against Neovim v0.10, v0.11, v0.12, and nightly.
- `make doc` / `make doc-check`: regenerate help from `lua/hgsigns/config.lua` and fail if docs drift.
- `make format-check` or `make format`: lint or autoformat Lua sources with Stylua.
- `make emmylua-check`: run EmmyLua static analysis (fetches analyzer on first run).
- `make commitlint [COMMIT=<sha>] [RANGE=<a>..<b>]`: validate commit message style.
- Read `etc/testing.md` for the test matrix, test-selection guidance, and troubleshooting notes.

## Coding Style & Naming Conventions

- Lua code must have EmmyLua/LuaCATS type annotations.
- 2-space indentation, 100-character columns, single quotes for strings.
- Run `make format` and `make emmylua-check` after changing any Lua code.
- When creating simple util functions, check Neovim's `:help` first to avoid reimplementing builtins.
- All `hg` invocations must include `HGPLAIN=1`, `LC_ALL=C`, and
  `--config ui.relative-paths=false`; see `PORTING.md` §5 for why.

## Testing Guidelines

- Add or update tests for risky, non-obvious, or broad changes; see `etc/testing.md` for details.

## Commit & Pull Request Guidelines

- Read `etc/commit-message.md` before creating or amending commits.
- Read `etc/pull-request.md` before pushing a branch or opening a PR.
- Ensure `make build`, the relevant `make test-*`, and `make doc-check` all pass locally.
- Treat failed required local checks as blocking unless the user explicitly approves proceeding
  with known failures.

## Tracking & Porting Upstream (gitsigns.nvim)

The upstream remote is `upstream` (https://github.com/lewis6991/gitsigns.nvim).
The upstream default branch mirrors into local branch `main` (not the `mercurial` worktree branch).

### Checking for New Upstream Work

```bash
# Fetch latest upstream without merging
git fetch upstream

# See commits on upstream/main not yet in this branch
git log HEAD..upstream/main --oneline

# Show full diff of what upstream added
git diff HEAD upstream/main
```

### Cherry-Picking a Single Upstream Fix or Feature

Follow the checklist in `PORTING.md` §7.  Quick summary:

1. `git cherry-pick -n -x <sha>` — stage without committing (`-x` records the upstream SHA in the commit message).
2. Fix any un-renamed identifiers (`gitsigns` → `hgsigns`, etc.); see `PORTING.md` §2.
3. Drop hunks that touch **removed subsystems** (staging area, worktree support, CRLF,
   index-edit path); see `PORTING.md` §4.
4. Translate new `git` CLI calls to their `hg` equivalents; see `PORTING.md` §3.
5. Wrap new `hg` calls in the stabilization env (`HGPLAIN=1`, `LC_ALL=C`,
   `--config ui.relative-paths=false`); see `PORTING.md` §5.
6. Run `make test` and `make format-check`.
7. Commit with a message referencing the upstream SHA:
   `git commit -m "port: <subject> (upstream <short-sha>)"`

### Porting a Batch of Upstream Commits

```bash
git fetch upstream
# cherry-pick a range onto the mercurial branch
git cherry-pick -n <oldest-sha>^..<newest-sha>
# resolve conflicts, apply rename map, drop removed subsystems
make test && make format-check
```

### Keeping the Upstream Mirror Branch Current

```bash
git fetch upstream
git checkout main
git merge --ff-only upstream/main
git checkout mercurial
```

### Identifying Conflicts vs. Mechanical Renames

When a cherry-pick produces conflicts, check whether the conflicting lines are
*only* identifier differences (`gitsigns` ↔ `hgsigns`).  If so they are
mechanical — apply the rename map and move on.  Conflicts that touch actual VCS
command arguments require VCS translation (see `PORTING.md` §3).

### Files to Watch in Upstream

These upstream files are most likely to carry meaningful changes worth porting:

| Upstream file                        | Hgsigns equivalent                    | Risk level |
|--------------------------------------|---------------------------------------|------------|

| `lua/gitsigns/git/repo.lua`          | `lua/hgsigns/git/repo.lua`            | High — VCS layer |
| `lua/gitsigns/git/blame.lua`         | `lua/hgsigns/git/blame.lua`           | High — VCS layer |

| `test/gitsigns_spec.lua`             | `test/hgsigns_spec.lua`               | Medium — replace `git()`→`hg()` |
